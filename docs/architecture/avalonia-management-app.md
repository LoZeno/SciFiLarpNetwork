# Avalonia management application baseline

The desktop administration client is a .NET 10 Avalonia application in `Management/src`. It is an API client, not a database or event-store editor. It discovers the API version and advertised navigation through the Siren profile and follows only links within the configured `/api` path and origin. Advertised actions are submitted only explicitly, and the initial client supports JSON request bodies.

Run the app from the repository root with:

```powershell
dotnet run --project Management/src/SciFiLarpNetwork.Management.csproj
```

The app reads and saves `appsettings.json` in the same directory as its executable. The shipped defaults use API address `http://localhost:5000/api` and locale `en`; the connection panel saves the last API address and selected English/Italian locale back to that file. Keep a backup of local edits before rebuilding or redeploying, as publishing or replacing the application can replace the settings file. The executable directory must be writable for changes to persist; if the file is missing, unreadable, malformed, or cannot be saved, the client falls back to defaults where applicable and shows a localized warning.

Existing preferences in `%APPDATA%/SciFiLarpNetwork/management-settings.json` are not imported automatically. To keep them, copy the `apiBaseUrl` and `locale` values into the `appsettings.json` beside the executable before launching the new version.

After a local operator bootstraps an administrator, enter the account name and password in the connection panel, select **Sign in**, then **Connect** to refresh authenticated navigation. After signing in, the account and password fields fold away and are replaced by **Administrator: <account name>**, **Sign in** turns into **Sign out**, and **Connect** appears; signing out reverses all three. After a successful connection **Connect** reads **Reconnect**. Selecting a navigation entry opens it immediately, without locking the connection buttons or changing the connection status unless the entry fails to open. The client holds the session token only in memory, sends it only to its issuing API, and clears it and protected navigation on logout or an expired-session response. Remote administrator connections require HTTPS. The [administrator guide](administrator-authentication.md) describes bootstrap, recovery, session expiry, and roles.

The client provides the desktop shell, connection status, advertised navigation, resource summary, and advertised-action list. It always uses a dark sci-fi look: cyan-edged panels and buttons with cut corners, defined in `Management/src/Styles` and `Management/src/Views/Hud`. Changes are animated: navigation entries drop down below the **Navigation** heading after **Connect** and fold back up on sign-out, and on each navigation the current view slides out to the left before the opened screen slides in from the left. Navigation entries without a purpose-built screen show the resource summary.

The **Talents** entry opens the talents and skills screen ([MANAGER-02](../specifications/legacy-features/manager-tabs/MANAGER-02-skills.md)). It lists talents on the left and the skills of the selected talent on the right; each list has a **Show archived** option, and archived entries are marked. Administrators get **New**, **Edit**, and **Archive**/**Unarchive** buttons for both lists; readers only browse, because the API advertises no change actions to them. Talents and skills are edited in modal dialogs. The skill dialog covers cost, flags, talent assignment (archived talents appear only when already assigned), game flags, existing and newly typed card flags (one name per line), and prerequisite groups: the character needs every group, and any one skill in each group. Archived prerequisites are listed in a warning but can still be saved. Archiving and unarchiving ask for confirmation. Validation and server errors appear inside the dialog, which stays open; a stale edit shows the conflict and reloads the latest values. The screen follows only advertised links and actions and never builds API addresses itself.

The **Networks** entry opens the networks screen ([MANAGER-11](../specifications/legacy-features/manager-tabs/MANAGER-11-networks.md)). It lists networks with their code and marks the default and disabled ones; a search box filters by name or code, and **Show disabled** includes disabled networks. A warning appears when no default network is set. Administrators get **New**, **Edit**, **Make default**, and **Enable**/**Disable**; the default network cannot be disabled, and each of these state changes asks for confirmation. The network dialog edits the name, description, theme, and background image; the code can be typed only when the network is created. **Choose image…** opens a file picker for a PNG, JPEG, or WebP file of up to 2 MB and 4096 × 4096 pixels and shows a preview; if the saved image cannot be downloaded or decoded, the dialog still opens without a preview so the image can be replaced or removed; **Remove image** goes back to the theme's background image. The image change is sent when the dialog is saved, after the details. As with the talents screen, errors appear inside the dialog and a stale edit reloads the latest values.

The **Players and Characters** entry opens the players and characters screen ([MANAGER-01](../specifications/legacy-features/manager-tabs/MANAGER-01-players-characters.md)). Players are listed on the left, 50 per page with **Previous** and **Next**, each with its running number; a search box finds players by name or number, and **Show archived** includes archived players. Selecting a player lists their characters on the right, also 50 per page with **Previous** and **Next**. A second search box finds characters of every player by name or number, and a QR identifier box finds the character with that identifier; both show their results in the character list, with the player's name, until **Back to the player's characters**. Administrators get **New**, **Edit**, **Make inactive**/**Make active**, and **Archive**/**Unarchive** for players, and **New**, **Edit**, **Archive**/**Unarchive**, and **New QR identifier** for characters; making a player inactive retires their active characters, and every one of these state changes asks for confirmation. The character dialog edits the name, title, species, gender, type, and experience points; for a saved character also the status, the date of death, and the QR identifier shown read-only. It shows the default network as always included and offers one other enabled network, and lists every stat with this character's value; new stats are typed with a name, a type (Number or Text), and a value; the stat becomes part of every character, and that first value is the starting value for all of them. **Character stats…** opens a window to rename, archive, and unarchive stats. As on the other screens, errors appear inside the dialog and a stale edit reloads the latest values. Readers and administrators can select one or more characters in the character list (Ctrl or Shift for several) and print their cards ([MANAGER-13](../specifications/legacy-features/manager-tabs/MANAGER-13-character-cards.md)): **Preview cards** saves the PDF to a temporary file and opens it in the computer's default PDF viewer, and **Export cards…** asks where to save it. Cards are printed in the order the list shows them. Each preview deletes preview files more than a day old. While several characters are selected, **Edit**, **Archive**/**Unarchive**, and **New QR identifier** are off; reloading the list keeps only the current character selected. The selection covers one page, so at most 50 cards print at once. Skill purchases are made by [MANAGER-12](../specifications/legacy-features/manager-tabs/MANAGER-12-character-skills.md).

The **Events** entry opens the events screen ([MANAGER-03](../specifications/legacy-features/manager-tabs/MANAGER-03-events.md)). Events are listed on the left, 50 per page with **Previous** and **Next**, newest first day first, each with its running number, dates, and status; **Show archived** includes archived events. Selecting an event lists **All days** and then each day with how many characters are registered; selecting one lists those characters on the right with their player, registered days, and the experience given at the event, and the experience history of the selected character below. Administrators get **New**, **Edit**, **Close**/**Reopen**, and **Archive**/**Unarchive** for events, **Add day**, **Edit day**, and **Remove day** for days, and **Register character**, **Unregister character**, and **Change experience** for participants. The registration dialog searches characters by name or number and lists the event's days; days the character already has are shown and cannot be picked again. Unregistering removes the selected day, or every day when **All days** is selected. The event dialog has optional **Base event experience points** and the day dialog optional **Experience points for this day**. **Close** opens a grid of the registered characters, a base column, and one column per day, with a checkbox for each experience that can be given; checkboxes start ticked except for Retired, Dead, or archived characters, and two buttons tick or clear all day or all base checkboxes. A warning reminds that experience cannot be changed after closing. Closing asks to confirm the selection, then gives each character the ticked experience. After a reopen, experience already given shows as **given**. Reopening and archiving ask for confirmation. A Closed event shows why it cannot change, and these buttons are off. Readers and administrators can **Preview cards** and **Export cards…** for the characters of the selected day or of every day; each card shows the character's first and last registered day.

The **Messages** entry opens the messages screen ([MANAGER-04](../specifications/legacy-features/manager-tabs/MANAGER-04-messages.md)). Messages are listed on the left, 50 per page with **Previous** and **Next**, newest first, each with its time, sender, title, and number of recipients. A search box finds characters by name or number; choosing one lists only that character's incoming messages, and **All messages** lists every message again. Selecting a message shows its title, sender, time, sending administrator, recipients, and text on the right; the text is shown exactly as sent in a read-only box that scrolls, and so does a long recipient list. Archived characters are marked and a character that cannot be found is shown as unknown. Every opening is recorded by the server; the message shown right after sending it is not an opening. The list updates in real time: when anyone sends a message, the screen reloads the page it shows if the message belongs on it, keeping the page, the selected message, and its details. If the connection drops, a note on its own line under the status says the updates are interrupted while the app reconnects: at once, after 2 and 10 seconds, then every 30 seconds, for as long as the screen is open. When it comes back the page is reloaded. If the backend refuses the session, or live updates are not available at all, a note says that new messages appear only when the list is loaded again. Leaving the screen or signing out stops the updates. A reply shows the message it answers, and **Open original** shows that message. Administrators get **New** and **Reply**. The message dialog finds characters and offers **Set as sender** and **Add recipient**; a character is listed once, and the dialog shows how many of the 200 recipients are used. **Reply** starts from the listed character (or the first recipient) as sender, the original sender as recipient, and the title with `Re: `, cut to the 128-character limit; every field can be changed. **New** on a filtered list starts with that character as recipient. Errors appear inside the dialog, which stays open; saving again sends the same message identifier, so a message is never sent twice.

The **Card templates** entry ([SPEC-29](../specifications/SPEC-29-card-templates.md)) shows the **Character cards** template as **Default** or **Uploaded by** an administrator with the date and time. Readers and administrators can **Download** it. Administrators also get **Preview file…** (prints the sample cards with a chosen `.typ` file, saves nothing, and opens the PDF like **Preview cards**), **Upload…** (the server prints the sample cards first and saves the file only if that works), and **Reset to default** (asks for confirmation; off while the default is used). A file over 256 KB is refused before it is sent. When Typst rejects a file, its error is shown in a read-only box under the buttons. A stale upload or reset reloads the template so the next try uses the latest version.

Account-creation, role-editing, and the other feature-specific administration screens are not yet provided. UI assets and localization resources are local. Runtime access is limited to the configured API; no web server, direct database connection, external identity provider, or remote content is used by this desktop client.

Building and launching this baseline on the Windows ARM64 development host does not establish support for all six approved runtime identifiers. Per-target build, packaging, and launch evidence remains a release gate under SPEC-07 and the later CI/deployment specifications.
