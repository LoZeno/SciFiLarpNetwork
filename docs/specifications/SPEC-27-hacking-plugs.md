# SPEC-27: Hacking plugs

## Purpose and prerequisites

Replace the legacy code-breaking plug (“spina di decodifica”) with two kinds of configurable in-game plug, defined by administrators in the management application and applied by the server when a hacking challenge starts. Plugs are game props. They are not authentication credentials and not a real security control.

Implement this after [SPEC-26](SPEC-26-hacking-game-settings.md) and [CROSSCUT-04](CROSSCUT-04-hacking-simulation-rules-update.md), and before [CROSSCUT-03](CROSSCUT-03-server-authoritative-hacking-challenges.md), which calls the rules below at challenge creation. Also follow [SPEC-24](SPEC-24-event-store-runtime.md) and [SPEC-25](SPEC-25-administrator-authentication-authorization.md).

The legacy behavior is documented in [old-hacking-system.md](../references/old-hacking-system.md): a plug code won automatically when the plug level was strictly greater than the difficulty, and every plug could be reused without limit.

## Plug model

A plug has a generated identifier, a name (required, 1–64 characters after trimming, unique and case- and Unicode-normalization-insensitive), a redeemable code, a kind, a usage mode, and an archived flag.

### Kinds

| Kind | Fields | Effect |
|---|---|---|
| Guarantee | `level` (whole number, at least 1) | The challenge succeeds when the difficulty is **less than or equal to** `level`. The typing game is not played. |
| Boost | `boostLevels` (greater than 0, at most two decimal places), `ceilingDifficulty` (whole number, at least 1) | When the difficulty is less than or equal to `ceilingDifficulty`, the effective hacking level is the hacking level plus `boostLevels` (see SPEC-26). |

There is no maximum for `level`, `boostLevels`, or `ceilingDifficulty`. A boost can express extra fractions of ability, for example 0.5.

### Usage modes

| Mode | Behavior |
|---|---|
| Single-use | The plug can be used once. After its use it is exhausted. |
| Limited | The plug has a number of remaining uses (a whole number, at least 2 when created) and loses one with each use. At zero it is exhausted. |
| Permanent | The plug is never exhausted. Each use is still recorded. |

Both kinds can use any mode. Administrators can edit the remaining uses of a single-use or limited plug. A single-use plug that was used can be given a use again by editing it.

## Rules

- A character whose hacking level is below 1 cannot start a challenge, even with a plug (SPEC-26).
- A challenge accepts at most one plug.
- A plug applies only to targets that accept plugs. Each consuming feature declares per target category whether plugs are accepted. The default is not accepted. A plug presented to a target that does not accept it is rejected, and no use is spent.
- A plug that is archived, exhausted, unknown, or not applicable to the target's difficulty is rejected with a stable error. No use is spent. The error does not reveal the target's difficulty.
- A guarantee plug that applies spends one use when it is applied, and the challenge ends immediately as a success. The success is recorded and audited the same way as a played challenge.
- A boost plug that applies spends one use on **every attempt** at which it is applied, whether the hack then succeeds, fails, or expires. A use is never refunded.
- The use is spent in the same atomic commit that starts the challenge. If the challenge cannot start, no use is spent.
- Concurrent use of the last remaining use of a plug is decided by Marten's optimistic concurrency. The plug is loaded with `FetchForWriting` and exactly one command wins. The other receives the stable “plug exhausted” error and spends nothing.
- The plug itself, its kind, level or boost, usage mode, and remaining uses are always resolved on the server. The client sends only the code.

## Codes

- A plug code is generated by the server from a cryptographically secure random source, with at least 64 bits of entropy, in a form that is practical to type (for example groups of characters from the CROSSCUT-03 alphabet). Codes are unique after normalization (trimmed, case-insensitive).
- Codes are redeemed by typing them when starting a challenge. Scanning a code through [CROSSCUT-01](CROSSCUT-01-qr-capture.md) may be added by a consuming feature.
- A code is a bearer value, like a physical prop. Whoever has it can use it.
- Codes are never written to logs, URLs, or error details.

## Management application

- Add a “Hacking plugs” entry to the management navigation. Administrators with read permission can list and inspect plugs. Only administrators with write permission can change them.
- The list shows name, kind, level or boost and ceiling, usage mode, remaining uses, and whether the plug is archived. Archived plugs are hidden by default and clearly marked when shown.
- Administrators can create and edit plugs, regenerate the code (which invalidates the old code), set the remaining uses, and archive and unarchive plugs. Archiving and regeneration require confirmation. Nothing is deleted.
- The code is shown to the administrator at creation and after regeneration, so it can be printed or handed to players.
- Each plug has a use history: time, acting character, target category, challenge identifier, and whether the use was a guarantee or a boost.
- All text is localized in English and Italian.

## Event sourcing

- Plug definition changes and every use are auditable events in the plug's own stream, following SPEC-24: load with `FetchForWriting`, carry expected versions, and commit with one `SaveChangesAsync`. A use is appended in the same Marten session as the challenge initiation event so both commit atomically.
- Creation commands follow the retry-safe pattern of SPEC-24 (a deterministic stream identifier for the creation command).
- Register every plug event type with Marten and evolve payloads only through upcasting.
- Events never contain the plain code (see Open decisions).

## Acceptance criteria

- Administrators can create, edit, archive, unarchive, and regenerate plugs of both kinds in all three usage modes, with validation of every field.
- A guarantee plug of level N succeeds against every difficulty from 1 to N, including N itself, and is rejected for higher difficulties without spending a use.
- A boost plug adds its fractional levels only up to its ceiling difficulty, and spends one use on every attempt, including failed and expired attempts.
- A single-use plug can be used once. A limited plug lasts exactly its number of uses. A permanent plug is never exhausted, and all uses are recorded.
- Two simultaneous uses of the last remaining use result in one use and one stable rejection.
- A level-0 character, an archived or exhausted plug, an unknown code, a non-applicable difficulty, and a target that does not accept plugs are all refused without spending a use.
- The management client, the backend API, and the English/Italian resources handle invalid input, stale edits, and persistence failures clearly.

## Verification

- xUnit tests cover both kinds at the `<=` boundary and one level above it, fractional boosts, every usage mode, spending on success, failure, and expiry, atomic commit with challenge initiation, concurrent use of the last use, refusal cases, event emission, authorization, and concurrency conflicts.
- API tests verify discovery, validation, and that clients cannot supply plug properties, remaining uses, or the effect of a plug.
- Tests verify codes are absent from event payloads, logs, URLs, and error details.
- Management-client tests cover listing, creating, editing, archiving, regenerating, use history, and error display.

## Open decisions

- **Code storage.** The proposal is to store only a hash of the normalized code (codes have at least 64 bits of entropy) and show the code once at creation or regeneration. This follows SPEC-24's rule against reusable secrets in events. The alternative is to store the code so administrators can view it again, which needs an explicit exception to that rule. Administrator-typed memorable codes are not supported by the proposal because they have low entropy.
- **How a character obtains a plug.** This specification treats a code as a bearer value typed at challenge start, as in the legacy system. Per-character ownership or an inventory item is not defined.
- **Guarantee plug presentation.** The proposal is that the challenge ends at once as a success. Whether the interface still plays a short non-interactive sequence is a presentation decision for CROSSCUT-04.
- **Which target categories accept plugs.** The default is none. Each consuming feature decides.
